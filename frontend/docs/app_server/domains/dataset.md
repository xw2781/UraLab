# App Server Domain: dataset

## Purpose
<!-- MANUAL:BEGIN -->
Dataset retrieval/patch domain for in-memory dataset instances.
Also handles reserving-class dataset file discovery and sidecar metadata, including the only persisted dataset/method Notes field.
See [`server-components/docs/dataset-scenarios.md`](../../../../server-components/docs/dataset-scenarios.md) for the source-kind scenario matrix, editability rules, and cache rebuild behavior.

## External Interfaces
<!-- MANUAL:BEGIN -->
- Called by Dataset Viewer and DFM frontend flows via `ui/shared/dataset/dataset_api.js`.
- `GET /dataset/{ds_id}` and `GET /dataset/{ds_id}/diagonal` require `project_name` and `origin_length` query values. The registered CSV path must be inside that project's data folder, then origin labels are always requested from the current ArcRho project headers rather than reused from potentially stale sidecar labels. Embedded project-name fields may remain stale after a supported project copy or rename and are not used for ownership checks. Header loading validates the project's Origin Start Date before using a cache and invalidates header caches older than `general_settings.json`. Labels must use the annual, half-year, quarterly, or monthly date format matching `origin_length`, be consecutive, and exactly match the CSV row count. Missing/invalid settings or labels return `422`, header-generation timeouts return `504`, and filesystem/lock failures retain their server error status; no route synthesizes labels from a default year.
- Exposes a notes save endpoint that performs a locked read-modify-write of the owning dataset sidecar; Notes load as part of the sidecar or aggregate cache response.
- Method-backed sidecar save responses include canonical `unreviewed_precedents` and `unreviewed_precedent_count` fields so every method window can present the same non-blocking post-save review warning.
- Exposes `GET` and `PUT /dataset/number-format-defaults` for the workspace-global `config/dataset_number_formats.json`. Override rows are keyed only by `dataset_type_name`; the same type format applies across all reserving-class paths. Saves validate nonblank fields, reject duplicate Dataset Type Name keys, use revision checks to prevent stale-window overwrites, and replace the JSON atomically. The GET accepts an optional `dataset_type_name` query value and returns the canonical resolved format plus decimal places for temporary Dataset Viewer opens.
- Exposes dataset sidecar load/save endpoints. Dataset sidecars live in `projects/<project>/data/<ReservingClassFolder>/sidecars/<DatasetName>.json`; `dataset_name` is the persisted user-visible instance name, `dataset_type` is the persisted Dataset Type, `origin_labels` stores persisted row labels when supplied by method pages, `number_format` stores the Dataset Data tab numeric display pattern, `decimal_places` stores its fractional digit count, `method_type` stores `None`, `DFM`, `Result Selection`, or another method type, `status` stores `0` for current and `2` when a method-backed output needs human review, and `audit_log` is always the last field and stores records with `event_date`, `action`, `change_info`, and `user` under the one audit policy owned by `arcrho_api.sidecar_audit_contract`: every action is kept (including the Engine's `Auto Refresh`), a run of consecutive automatic entries collapses to its most recent member, and the newest `DATASET_AUDIT_LOG_MAX_ENTRIES` (200) remain. Every sidecar — engine cache, app-saved dataset, or method output — shares the core checked by `arcrho_api.sidecar_core_contract.validate_sidecar_core`; the five contract builders validate before returning, and every app-server write funnel runs `with_audit_log_last` so a save that merged an older file still lands the log last. Every save resolves the saving account's Windows login through the workspace-global `config/username_index.json` and stores that configured full name in `user`, `modified_by`, and each audit record, falling back to the unmapped login when the account has no mapping. Every sidecar records two period shapes, following ResQ's naming. `origin_length`/`development_length` — `period_length` on a vector — are the **display** shape the dataset is shown and saved at, the counterpart of ResQ's `OriginLength` family. `stored_origin_length`/`stored_development_length` — `stored_period_length` on a vector — are the **stored** shape, the months per period of the CSV named by `csv_file`, the counterpart of ResQ's `StoredOriginLength`; every sidecar of every source kind carries the pair its format takes, built by `arcrho_api.sidecar_core_contract.stored_length_fields`. The display shape must be a whole multiple of the stored shape on each axis, because any coarser view is a roll-up computed when the dataset is read and is never written back: the CSV stays at the stored shape and only that file is ever the dataset's data. Which pair a reader takes follows from what it is about to do: every read that opens the file `csv_file` names asks `arcrho_api.sidecar_core_contract.stored_lengths` for its shape — the DFM and Bornhuetter Ferguson / Cape Cod / Bootstrap precedent checks, the shared precedent resolver, the blank-cell patch mask, the Berquist Sherman annual check, the Excel-link save and the cached dataset load — while a read that asks for a regeneration (the Engine's source refresh, a calculated output's next build) or that names what a page is showing keeps the display pair. A method whose precedent is stored finer than its own period brings it to that period rather than refusing it: `precedent_cache_service.precedent_source` rebuilds an Engine-generated precedent at the method's period and reads a hand-entered one from its own CSV for an in-memory roll-up, the same two moves the DFM makes; only a precedent stored coarser than the method is refused, since its figures cannot be split. A hand-entered dataset is stored at the shape its values were entered at, a calculated or method output at the period it was produced at, and a generated dataset at the granularity of its source data. A dataset imported from ResQ takes ResQ's own stored lengths (`StoredOriginLength` / `StoredDevelopmentLength`, `StoredPeriodLength` on a vector): a generated dataset is stamped with them, which in a monthly project is 1 whatever period ResQ displayed it at, and a hand-entered triangle or vector is read at that shape — the import shows the dataset at its stored lengths for the read and restores the displayed ones, the same switch the export macro makes before writing values — so the finer figures leave ResQ and the CSV is written at them (`resq_migration.extractors.export_triangle` / `export_vector` with `at_stored_shape`); a calculated dataset and a method output keep the shape ResQ displayed, since ArcRho recomputes the one and the method owns the other. Triangle sidecars also store `cumulative` and `calendar`. A sidecar that holds a cell link of any kind records a third shape, the **linked** one — the development width `linked_development_length`, built by `arcrho_api.sidecar_core_contract.linked_length_fields` and read, with the origin axis beside it, by `linked_lengths`. It is the display the links were written against: a link names a cell of the grid on screen when it was entered, so the display can move on and be saved while the links keep pointing into that grid. Only the development axis is recorded, because only it can differ. A link can be entered only where the grid can be typed into, and on the origin axis that is the stored period: a coarser origin row is the calendar diagonal of several stored rows, has no single cell to write back to, and locks the whole grid read-only, while a display finer than the store is refused while the dataset holds values. `linked_lengths` therefore reads the origin axis from `stored_lengths` and never from a display that may have moved on since the links were written; a triangle that states no linked width was saved with its links at the display it records, and a vector, having one axis and it the stored one, records nothing at all. `linked_origin_length` and `linked_period_length` were written before that was understood, are listed in `RETIRED_SIDECAR_FIELDS`, and are dropped from any sidecar a save rewrites. A save stamps the linked width with the one its `values` come at whenever the links it carries differ from the sidecar's, keeps the recorded width whenever they are the same, and drops it when no link is left. A link refresh — the Excel retarget and the Engine's `dataset_link_refresh_service` — reads the dataset at the linked shape (`load_cached_dataset_values(at_linked_shape=True)`, the same roll-up the window uses for `at_display_shape`), writes the linked cells there, and puts them into the store the way a save from that view does (`scatter_view_into_store`); the retarget save passes the sidecar's display pair as `display_at` so the shape the values come at and the display the sidecar records stay separate. Editable Dataset Excel sources are stored as `external_links`, an array of `{reference, target_cells}` records where each target contains zero-based `{row, column}` logical Dataset coordinates and a normalized A1 `source_cell`; Dataset coordinates remain untransposed even when the client displays the grid transposed. Each saved reference must be a standalone workbook cell/range, each mapped source cell must belong to that reference, and target ownership cannot overlap another record. Explicit source cells allow the normalized target list to contain only the editable destinations reached by a larger range after grid-boundary or triangle-mask clipping; non-strict loads keep the first valid target owner and discard malformed or ambiguous later records. Insert records leave `change_info` blank; update records use `Values`. Sidecar load/save responses include normalized `external_links`, `Precedents`, and `Dependents`; a missing external-link field loads as `[]`, omitting `external_links` from a save preserves the existing field, and sending `[]` clears it. Graph entries support Dataset Details dependency navigation: precedent entries include resolved `method_type` for method-backed formula component navigation, and dependent entries include formula text when the dependent sidecar or Dataset Type formula can be resolved. A sidecar load reads the Dataset Type configuration and selected-path dataset index once, then reads related graph sidecars with bounded parallelism so mapped-drive latency is not paid serially for every precedent and dependent. The old root aliases `instance_name` and `dataset_type_name` are not accepted. Save updates metadata, appends a sidecar audit record, preserves caller-supplied `source_kind`/`data_format`, applies current formula graph fields without replacing method-owned precedents, and marks transitive method-backed dependents as needing review while leaving app-calculated `method_type: None` outputs unflagged. It then recalculates existing app-calculated outputs and eagerly refreshes registered Result Selection dependents from the durable source/basis cache; successful RS refreshes clear their review status, while failures remain explicit in `calculated_updates` and preserve the previous RS artifacts. One reserving-class index rebuild occurs after the combined cascade. When the save payload includes `values` and `mask`, the service also writes the current numeric/`null` snapshot, not Excel formulas, to the format-scoped CSV under `datasets/` (`<DatasetName>@<PeriodLength>.csv` for vectors, mode-qualified origin/development names for triangles), stores that file name in `csv_file`, registers the CSV-backed `ds_id`, and returns the CSV modification time for follow-up grid edits. The CSV is restored to its prior version if the paired sidecar replacement fails, preventing new values from being left behind without their external-link metadata; if the restore is itself blocked, the rollback copy is retained and its path is reported for recovery.
- `dataset_service.triangle_grid_shape` is the one answer to where a triangle's cells stop: `_empty_dataset_geometry_from_general_settings` counts the origin rows from the Origin Start and Origin End Dates, the development columns back from the Development End Date, and keeps the cell at `(r, c)` when `origin_start + r * origin_length + c * development_length` is on or before that date. The same geometry writes a new empty CSV, so a grid drawn from this read and the file the save writes have the same shape. A Dataset window building a hand-entered grid that has no file yet -- a Project Instance draft, or a cleared dataset rebuilt at new lengths -- reads it through `GET /datasets/triangle-shape`, and `load_cached_dataset_values` narrows a `source_kind: "input"` triangle's mask with it so a figure stored past the diagonal is neither served as a cell nor written back. A Vector has no diagonal and is never narrowed.
- Editable Dataset cells can also link to another dataset of the same reserving class through `internal_links`, the ArcRho sibling of `external_links`: an array of `{reference, target_cells}` records whose `reference` is a standalone `=[Dataset][rows]` or `=[Dataset][rows, cols]` text in the DFM dataset-reference index style extended with an inclusive `start:end` range, and whose target cells carry zero-based untransposed `{row, column}` plus the referenced dataset's zero-based `{source_row, source_column}`. `app_server/services/dataset_internal_link_service.py` owns the standalone-reference syntax, the canonical stored text, and `POST /dataset/internal_links/resolve`, which resolves references with one `load_cached_dataset_values` read per unique referenced dataset; the per-axis index semantics (quoted label, 1-based position, negative from the valid boundary, bare-label fallback for numeric labels such as origin years) are the DFM resolver's own helpers, so one syntax never resolves two ways. The resolve is registered as the hosted workspace read `dataset_internal_links_resolve`, so a Client PC pays one HTTP round trip instead of one SMB visit per referenced dataset. Saves validate the field strictly (`400` on a malformed reference, a duplicate target or source cell inside a link, or a target owned by more than one link), refuse a cell linked to both an Excel workbook and an ArcRho dataset, preserve the field when omitted, and clear it on `[]`; loads normalize leniently and a missing field loads as `[]`. A committed ArcRho link is a graph edge as well as a value source: the save records the referenced datasets as instance-level `precedents` on the linked dataset and writes the matching `dependents` entry on each referenced sidecar (`arcrho_api.dataset_link_contract.link_precedent_names` is the one extractor every producer uses), and the Engine's dependent-propagation walk re-evaluates the links whenever a referenced dataset is refreshed, so linked values follow their sources instead of staying the snapshot of the last manual refresh. The Links-tab refresh remains the on-demand twin; only Excel-linked values (`external_links`) stay snapshot-only between explicit refreshes. Like `external_links`, the field is forbidden from the reserving-class `index.json` row projection.
- A cell whose value is calculated rather than copied is stored in `formula_links`, the third sibling: an array of `{formula, target_cells}` records whose `formula` is the canonical text of an arithmetic expression over dataset references, Excel references, and numbers (`=[C 82 - Prior Qtr Selected][1:7] * 2`), and whose target cells carry zero-based untransposed `{row, column}` plus the cell's `{result_row, result_column}` in the formula's result matrix. `arcrho_api.dataset_link_contract` owns the grammar, the canonical stored text, and the Excel array arithmetic, mirrored token for token by the client's `ui/shared/dataset/dataset_formula.js` — dataset references canonicalize through the internal-reference rules, Excel references keep their quoted source with an upper-cased address, binary operators are spaced, unary minus and parentheses are not — so the text a save sends is the text it reads back; `app_server/services/dataset_formula_link_service.py` delegates to it and translates its refusals into `422`s. The formula evaluates in the client on commit and Links-tab refresh, and on the server host inside the dependent-propagation walk (`dataset_link_refresh_service`); the save path validates what the sidecar may hold: strict on save (`400` on a formula that does not parse, one with no reference, a duplicate target or result cell inside a link, or a target owned by more than one link), lenient on load, preserved when omitted, cleared on `[]`, and a missing field loads as `[]`. One cell holds one link of any kind, so a save is refused when a target appears in more than one of `external_links`, `internal_links`, and `formula_links`. A formula's dataset references contribute the same instance-level `precedents`/`dependents` edges an internal link does; Excel references contribute no edge. The field remains forbidden from the `index.json` row projection.
- Link-driven datasets refresh inside the dependent-propagation walk. `dataset_link_refresh_service.refresh_dataset_links` re-resolves a plain-input dataset's `internal_links` by their stored source coordinates and re-evaluates its `formula_links` through the canonical contract — one `load_cached_dataset_values` read per unique referenced dataset, one batched workbook read for every Excel operand — then rewrites only the linked cells inside the current CSV grid and appends an `Auto Refresh` audit record. Failure semantics are asymmetric on purpose: an ArcRho-side problem (missing referenced dataset, non-numeric cell, a result that no longer covers the linked cells) fails the refresh, keeps the last values, and flags downstream methods for review like any dependency failure, while an Excel-side problem fails only the links reading that workbook — their cells keep their last values and the walk reports a warning (`propagation.link_warnings`, surfaced in the post-save notice with the dataset name clickable) because a workbook on another machine's local disk is routinely unreachable from the server host and must never block the chain. The ResQ import writes these links itself: a per-instance ResQ formula on a vector whose Dataset Type ArcRho treats as a plain input is translated into one whole-vector `formula_links` record when every referenced name is another imported vector of the class (`resq_migration.extractors._translated_instance_formula_links`); an untranslatable formula — a frozen prior-quarter snapshot reference, text outside the quoted-name grammar, a self-reference — falls back to importing the hardcoded values exactly as before.
- `show_subtotal` is sidecar-owned per dataset instance. Sidecar loads and saves normalize the field to a boolean, default missing or invalid legacy values to `true`, and preserve it across engine, calculated-dataset, method-output, public-API, and ResQ-migration refreshes. It remains detail metadata and is forbidden from the reserving-class `index.json` row projection.
- Exposes `/dataset/cache/load` for method pages and Project Instance Dataset Viewer opens that need numeric values from a named cached dataset. The route reads the canonical sidecar once, prefers its exact `csv_file`, can target an explicit file or requested origin/development length, and otherwise falls back to matching CSV names in the selected reserving-class `datasets/` folder. Exact requests are strict. `origin_length`/`development_length` in the response are the shape of the `values` returned and the `stored_*` pair (`stored_origin_length`, `stored_development_length`, `stored_period_length` on a vector) is the shape the dataset's own file is held at, read from the sidecar as the sidecar load and save read it. By default the values are the file's own rows, which is what a method page reading its inputs wants; with `at_display_shape` (sent only by the Project Instance Dataset Viewer open) a hand-entered dataset whose sidecar shows it coarser than its file is rolled up to that display shape through `precedent_cache_service.rollup_rows` on the project's valuation grid, registered under the handle of the file a dataset created at that shape would have (`register_rollup_handle`, so `GET /dataset/{ds_id}` serves the same view), and never written beside the file. The view's development labels are the project's headers cut to the columns the view has: the headers may run past the valuation date the view stops at (40 labels over 39 columns at a development length of 3), and a label count that differs from the column count is expected there, as it is when the run path lays the same headers over a grid. The response includes the grid model plus the sidecar-owned settings, notes, audit/graph payloads, and formatting needed for a two-file Project Instance DSV open; it does not enrich graph entries by scanning related sidecars or reread `index.json`. Valid sidecar origin and development labels are used directly. If an engine sidecar omits either axis, or persisted labels do not match the CSV shape/period, the route resolves the canonical project headers within the same aggregate request so the first grid paint receives exact labels; it never substitutes generic `12, 24, ...` development labels. The response also hydrates the Dataset Type formula from `dataset_types.json` for formula and Details presentation even though engine sidecars intentionally omit formulas. The origin-header, development-header, and Dataset Type hydration reads are independent network I/O and run concurrently on a bounded pool, with origin-label failures keeping precedence over development-label and formula failures; the small shared metadata files they read (`general_settings.json`, `dataset_types.json`, and ArcRhoHeaders label caches) are served through the mtime-validated in-memory cache in `app_server/services/file_read_cache.py`, so repeat opens cost stat calls instead of full mapped-drive reads while any timestamp or size change forces a re-read.
- For dataset sidecars, the no-IT Gateway changes only the transport of `/dataset/sidecar/save` and its dormant `/plan` sibling. The browser still calls the local app server, the HTTP request contains the exact canonical `ArcRhoHostedSave` payload, and ArcRho Engine still invokes `dataset_service.save_dataset_sidecar`; no sidecar, CSV, index, audit, response, dirty-state, or close behavior changes. Every other hosted save kind uses the same transport without widening the dataset contract.
- Exposes a project/path cached dataset lookup for Project Instance and DFM Details backed by the reserving-class `index.json` cache. The index resolves `project_name` plus selected reserving-class path to `projects/<project>/data/<ReservingClassFolder>`, then returns logical dataset names inferred from `datasets/*.csv`, `methods/*.json`, and `sidecars/*.json` metadata plus a folder signature derived from physical cache-file names, sizes, modification times, and folder existence. One canonical contract owns the index version, schema, minimal entry projection, normalization, and deterministic ordering, and the frontend app server, public Python API, ResQ migration, and mirrored macro emit the exact same full parsed payload for identical logical inputs. Persisted content is location-independent: absolute drive/UNC folder paths are added only to the app-server response from the frontend computer's current mapping. Returned `files` entries are scalar-only summary records with base dataset instance `name`, stored `dataset_type`, stored `dataset_category`, sidecar `data_format`, origin/development lengths when present, the matching `stored_origin_length`/`stored_development_length` pair projected from the sidecar's stored shape (a vector's `stored_period_length` lands under `stored_origin_length`, as its display period does under `origin_length`), latest modified time, earliest created time, user text and formula text stored in reserving-class metadata, `source_kind`, method type when applicable, and sidecar review status. Arrays and nested detail payloads are not indexed: `origin_labels`, dependency graphs, audit logs, and similar details remain in their owning sidecar or method JSON. Physical CSV, sidecar, and method records merge into one logical row without dropping origin/development length metadata; Result Selection uses that indexed native length to avoid rematerializing an already compatible engine source. Project Dataset Type formula/category defaults are resolved by consumers instead of being copied into `index.json`; the indexed `user` value remains the raw reserving-class-owned text; display-name resolution happens once when a writer stamps the sidecar, so the index and its consumers never remap it. Mode-qualified triangle cache filenames such as `<DatasetName>@12@12@cum@dev.csv` and vector period cache filenames such as `<DatasetName>@12.csv` are normalized to one base dataset instance entry; older two-length-only filenames are treated as literal stems instead of compatibility aliases. When a sidecar or method payload supplies `dataset_name`, that metadata name is the canonical logical row `name`, while filename-derived variants remain aliases for matching/deletion and do not create extra Project Instance rows. DFM uses `details tab.output dataset` or `output vector` as logical identity, falling back to `details tab.name` and then `output type`; when its method filename identity differs, scalar `method_name` identifies the matching `DFM@<method_name>.json`. Result Selection, Bornhuetter Ferguson, Cape Cod, and the two B&S formats use `details_tab.name`. Each method contract uses its configured output type as `dataset_type`, so prefixed physical method filenames do not create extra Project Instance rows. Reading a valid current index returns it without scanning detail files or rewriting/enriching it; rebuilds occur only after an explicit refresh, a durable mutation, or when the index is missing, invalid, or uses an outdated canonical version/schema. A read detects a durable mutation by listing the `datasets/`, `methods/`, and `sidecars/` folders once and comparing the resulting signature against the persisted `folder_signature`. That listing reads no sidecar or method payload, so an unchanged reserving class is served straight from `index.json` for the cost of three directory listings, and a write another producer made without updating the index is picked up on the next read instead of waiting for a manual refresh. When the signature does differ, the rebuild enumerates the folder again inside the index lock instead of reusing the unlocked listing, so an overlapping producer's write cannot be dropped from the payload that gets persisted. Explicit refreshes serialize writes per selected index path, write through unique temporary files, and briefly retry Windows sharing violations during the atomic replace so overlapping DFM saves, Sync pre-saves, and Project Instance refreshes do not collide on a shared `index.json.tmp`. Network and permission failures during a rebuild abort without replacing the last valid index.
- A read-only `GET /datasets/cached` lookup does not discard successfully scanned rows when the derived `index.json` cache cannot be replaced on a mapped drive. The response remains successful with `index_persisted: false` and an `index_warning`; those fields, the `index_signature` (the served `index.json`'s `<mtime_ms>:<size>` statted by the responding process, `missing` when the file is not on disk — the Project Instance staleness watch's authoritative baseline), and locally resolved `folder_paths` are response-only and never written into `index.json`. When an index must be scanned or rebuilt, directory enumeration stays deterministic while metadata JSON reads use a shared bounded worker pool; index writes remain serialized per selected path. Enumeration keeps the size and modification time the directory listing already returned instead of re-statting each path, so a rebuild costs no extra network round trip per cached file, and the canonical project and reserving-class names are resolved once per request and passed down rather than re-derived by each layer. Direct rebuilds after saves, deletes, and other mutations remain strict and report the persistence failure.
- Exposes cached empty dataset creation for Project Instance non-generated dataset types. The endpoint writes a zero-filled CSV under `datasets/` and base metadata sidecar under `sidecars/`, using the format-scoped filename convention and deriving the actual triangle/vector shape from the project's `general_settings.json` date boundaries. Missing, malformed, or invalid Origin Start, Origin End, or Development End settings return an actionable error instead of creating a default 12-by-12 dataset. For triangles, cells are included only when the origin period plus development period falls on or before `development_end_date`, so older origin periods have wider editable rows and newer periods narrow toward the latest diagonal. Dataset patch validation reuses that date-derived mask when sidecar metadata is available, resolves the current project from the containing project/data folder so copied or renamed sidecars may retain their old embedded name, and preserves Project Settings errors instead of silently falling back to a generic triangle; successful patch saves append an `Update` audit record to the related sidecar.
- Treats `dataset_types.json` rows with `Calculated=true` and `Generated=false` as app-calculated outputs. Adding one through Project Instance, requesting one whose output cache is missing, or saving a change to one of its component datasets recalculates the output under the selected reserving-class folder, marks the sidecar `source_kind: "calculated"` and `calculated: true`, and refreshes the selected reserving-class dataset index. When a requested app-calculated output has generated or app-calculated components, the runtime validates and materializes that direct chain upstream-first before evaluating the requested output. A background `WriteSidecar: false` cache load does not synchronously rebuild the full index or recalculate every existing dependent; calculated sidecars name each precedent only (the persisted graph is location-independent), while the formula that built the output and each precedent's exact path, data format, size, modification time, and SHA-256 digest are recorded in the per-CSV technical provenance record under `.arcrho-cache-provenance/`, so a later exact-cache check can reject a changed formula, same-stat content replacements, and old Vector/Triangle variants without the shared sidecar carrying any machine-local path. A calculated CSV without such a record offers no evidence and is recalculated on its next request. The check also compares the current formula/direct-precedent graph and recursively validates calculated and engine inputs, then recomputes only the stale requested chain. Exact DFM precedents keep their method JSON and input CSV identity, avoiding an ambiguous folder rescan; a stored absolute path from a different drive mapping is resolved by filename only within the current reserving-class roots. An unavailable or invalid Dataset Type contract fails safely without deleting the existing calculated CSV. Dependency discovery that has to search the reserving-class folder enumerates `datasets/` (or `methods/` for DFM outputs) once per component-resolution pass and reads the matching sidecar or method payloads through a shared bounded worker pool, deduplicating the sidecar paths that every cache variant of one dataset shares, instead of reading one sidecar per cached CSV in a sequential loop. Enumeration keeps the modification time the directory listing already returned, so no candidate path is stat-ed twice, and one component-loading pass reuses a single folder observation for all of its components rather than rescanning per dependency. Candidate scoring, ambiguity detection, and ordering are unchanged, so the same folder yields the same chosen dependency as before. Recalculation after an explicit persisted source change still follows the direct-dependent chain for app-calculated dataset types that already exist as instances in the selected reserving-class folder, so a source update in an existing `A -> B -> C` chain refreshes `B` before `C` but does not create or warn about absent calculated outputs. It returns ordered `steps` details to the caller. The `/dataset/calculated/preview` endpoint reuses the same formula evaluator with caller-supplied in-memory source values and returns downstream matrices without writing CSV, sidecar, or index files. Repeat component resolution is served from `class_folder_scan_cache`: sidecar and DFM method payloads plus component CSV matrices are cached in the app-server process and validated against the `(mtime_ns, size)` identities the directory listing already returned, so a repeat preview or recalculation over a network share costs directory enumerations instead of one read per file in the class. Entries written within the last few seconds are always re-read, failed reads are never cached, and results are copied on the way out; a tool that restores an old file while preserving its timestamp is outside the validation guarantee (same contract as `file_read_cache`).
- Exposes cached dataset deletion for Project Instance. The delete endpoint accepts project, reserving-class path, and logical dataset names, removes matching `datasets/`, `methods/`, related `sidecars/`, and matching technical runtime-provenance records only inside the selected reserving-class data folder, and rebuilds `index.json` afterward. Resolving which files a requested dataset owns lists `datasets/`, `methods/`, and `sidecars/` once and keeps the entry data the listing already returned instead of re-statting each path. Only method payloads are opened, because a method JSON keeps its dataset name in `details tab`/`details_tab` while a cached CSV and a sidecar are named after their dataset; on a mapped drive that removes one round trip per cached file plus one payload read per sidecar. The filename-derived match is verified rather than trusted: the rebuild is authoritative, so a requested dataset that still owns a row afterward means files survived, and only then is the sidecar payload read repeated and the rebuild redone. The response carries the rebuilt index under `index`, so the caller that requested the delete does not owe a second `/datasets/cached` read for the table it is about to redraw.
- Refuses to delete an object another object still reads. Before the first unlink the endpoint reads the requested datasets' own sidecars and collects their direct `Dependents` edges; if any dependent survives the request it removes nothing and raises `409` whose `detail` is an object: `error: "dataset_has_dependents"` (the canonical `dataset_instance_index_service.DELETE_BLOCKED_BY_DEPENDENTS`), a `message`, and `blocked_datasets` naming each refused dataset with its dependents' names and method types. The check covers the whole request before anything is removed, so a refusal leaves the selection exactly as the user found it rather than half-applied. A dependent that is itself in the same request is not reported, because deleting a method together with the input it consumes leaves no dangling reference behind. `blocked_datasets` lists direct dependents only — a deeper descendant reaches the target through one of them — while `downstream_closure` names the full transitive chain (each reachable object once, breadth-first, with its method type), which is what lets Project Instance offer deleting the selection together with everything that reads it in one confirmed resubmission: a request carrying the whole chain passes the same check, because nothing outside it survives. The delete also preflights the reserving-class propagation hold and is refused with `423` while a walk or queued job owns the class, so it cannot race the walk's own writes; no live Engine is required. The guard's reads are bounded by the selection (one sidecar per requested dataset, plus one per blocking dependent to label its method type, plus one per closure member when a refusal is being shaped) and run through the module's bounded pool, never one per file in the folder.
- Runs the whole delete on the ArcRho Server when the Gateway offers it, through the `cached_dataset_delete` mutation kind (see [`workspace_mutations`](workspace_mutations.md)). The dependency check, every unlink, and the index rebuild are local disk there instead of one SMB round trip each. The delete is idempotent -- a file already gone is skipped rather than failed, and the rebuild derives the index from whatever survives -- which is what allows that transport to keep no receipt.

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Uses in-memory dataset map and patch payloads.
- `GET /datasets/cached` (`dataset_index`) and `POST /dataset/cache/load` (`dataset_cache_load`) are Server-hosted workspace reads: when the Gateway advertises them, the index check/rebuild and the sidecar + CSV + label hydration run on the server host and the client rebases the returned `folder_paths`, `path`, and `sidecar_path` onto its own workspace root; a remote cache load registers its dataset `id` locally through `dataset_service.register_dataset_handle` so the id-addressed patch/diagonal routes still resolve. `GET /dataset/{ds_id}` (`dataset_grid_load`) is hosted the same way and falls back to the local registry when the Gateway does not know the handle. `GET /datasets/triangle-shape` (`triangle_grid_shape`) is hosted with them: it is one General Settings read, so a Client PC pays an HTTP round trip rather than an SMB visit for it. See [`workspace_reads`](workspace_reads.md).
- `arcrho_api.engine_dataset_sidecar_contract` owns the complete persisted engine-sidecar payload shared by frontend runtime generation and ResQ migration. Engine sidecars omit origin/development labels and Dataset Type formulas because cached reads hydrate those presentation values from project headers and `dataset_types.json`.
- An Engine-generated Triangle stops at the latest valuation diagonal: cells past the project's Development End Date are blank. An Engine-generated Vector keeps every origin period, because a vector has no development axis and the source table may carry full-year inputs (planned premium, exposure) for the origin periods after that date; a monthly vector in an August project therefore keeps its last four rows instead of showing zeros there. A negative row index on such a vector still counts back from the Development End Date, so `[-1]` is the valuation period (see the DFM domain doc).
- ArcRhoTri CSV request targets are `projects/<project>/data/<ReservingClassFolder>/datasets/<InstanceName>@<OriginLength>@<DevelopmentLength>@<cum|inc>@<dev|cal>.csv` when `InstanceName` is supplied, otherwise the Dataset Name is used. ArcRhoVec request targets are `projects/<project>/data/<ReservingClassFolder>/datasets/<InstanceName>@<PeriodLength>.csv`. The metadata sidecar is `sidecars/<InstanceName>.json` and records the generated instance as `dataset_name`, separately from `dataset_type`, plus `source_kind: "engine"`, `data_format`, `transposed`, `number_format`, `decimal_places`, `created`, `updated_at`, and user fields. New engine and app-calculated sidecars take `number_format` from the matching Dataset Type Name override in workspace-global `config/dataset_number_formats.json`, regardless of reserving-class path, fall back to its `default_number_format`, and derive `decimal_places` from the selected pattern; lookup uses sidecar `dataset_type`, not instance `dataset_name`, and later app-calculated refreshes preserve saved display settings. Triangle sidecars store `origin_length`, `development_length`, `cumulative`, and `calendar`; vector sidecars store `period_length`. Both also store the stored shape beside the display shape, as the sidecar section above describes. A generated dataset is rebuilt from the project's source table, so its stored shape is that table's own date granularity — `Origin Date` months on the origin axis, `Development Date` months on the development axis — read from the project's field mapping through `field_mapping_service.load_source_period_months`, whatever period the request asked to see it at. A project whose mapping records no granularity, and a sidecar of any other source kind that this write restamps, keep the requested shape. The ResQ import stamps the same fields from ResQ's `StoredOriginLength` family when it writes a generated dataset's sidecar (`resq_migration.extractors.write_engine_generated_export`), so an imported class agrees with the Engine's own rebuilds without waiting for one. The reserving-class path is a single filename-escaped folder name using the reversible `_%XX_` rule and is not repeated in the CSV filename.
- Project Instance non-generated placeholders are stored under `projects/<project>/data/<ReservingClassFolder>/datasets` with sidecars using `source_kind: "input"`. Draft saves persist the visible grid values to the format-scoped CSV file and update the sidecar `csv_file` field so custom entered values survive window reloads. A hand-entered dataset's own CSV is its data, so a save cannot move the shape that file is written at: the lengths a save carries become the display shape, while `stored_origin_length`/`stored_development_length` (`stored_period_length` on a vector) and `csv_file` stay exactly as the sidecar already records them. A save that carries `values` at a coarser **development** view of the stored shape is written the way ResQ writes one: each entered cell is that row's cumulative figure at its own valuation date, so `arcrho_api.triangle_rollup.scatter_triangle` -- the inverse of the roll-up that produced the view -- puts it in the stored cell valued at the same date and every other stored cell of the triangle becomes cumulative 0, an incremental grid being accumulated along the row first and the result written back in the sidecar's own convention. The origin axis is never relaxed, because a coarse origin row has no single valuation date to write to: a save whose origin length is coarser than the stored one is refused with `400` and `Values can be entered only at the stored origin period.`, and a vector -- which ResQ refuses a coarse write on as well -- keeps the `422` refusal for any period but its stored one. Such a save leaves the stored pair and `csv_file` exactly as they were. The one exception is a dataset whose stored CSV holds nothing but blanks and zeros: nothing is lost by relabelling it, so the shape asked for becomes the stored shape, the CSV is rewritten at it, and the file the dataset was stored at before is deleted. A save that carries `stored_values_cleared: true` is treated the same way whatever the file holds: the Data tab set every value to `0` and reshaped the grid before the values it sends were entered, so they replace the file at the shape asked for and the old file is deleted. Such a save may also ask for a store finer than the display, as ResQ's `Stored at` spinner does: the optional `stored_development_length` on the save request is the months per period the CSV is written at, so an empty triangle shown at 12/12 can be stored at 12/1 and the file it is rewritten to is named and shaped for the stored pair. The field is refused with `400` when it is not a factor of `development_length`, and with `400` when the stored CSV already holds a value and the length asked for differs from the one the sidecar records; the origin store has no control of its own and follows the origin length, and a vector — which ResQ refuses a stored period on — ignores the field. A save that names `csv_file` itself is publishing a file and states its shape, so it is outside the rule.
- App-calculated outputs also stay under `projects/<project>/data/<ReservingClassFolder>/datasets` but use `source_kind: "calculated"`, store `calculated: true`, store their formula and graph metadata in the sidecar, and are recomputed eagerly after editable component patch saves, explicit sidecar-backed ArcRhoTri saves, explicit sidecar saves, or Dataset Types formula saves. Background `WriteSidecar: false` reads do not trigger this chain. Sidecars use `Precedents` for direct formula inputs and `Dependents` for direct formula consumers; `Dependents` includes only direct formula consumers that exist as logical instances in the same reserving-class folder. Formula evaluation supports dataset references, DFM method output references, parentheses, and `+`, `-`, `*`, `/`; when a referenced DFM output CSV is missing, calculation can rebuild the DFM Results vector from the saved `methods/DFM@<Name>.json` method and its input triangle cache. Missing or ambiguous component caches skip the dependent update without failing the source dataset save.
- Result Selection output sidecars store `Precedents` as a plain string array of source dataset names, for example `["Paid Loss", "Reported Loss"]`, instead of formula graph entry objects. Result Selection output CSVs use the vector cache shape `<DatasetName>@<PeriodLength>.csv`; quarterly and half-year saves can also materialize coarser aggregate vector caches in the same `datasets/` folder while the sidecar `csv_file` remains pointed at the native-period CSV.
- ArcRhoTri precheck/execution treats a missing variant-specific CSV as a cache miss. When `InstanceName` is supplied, cache validation keys on the sidecar's decoded instance/dataset name plus project and reserving-class path, so manually imported datasets whose `dataset_type` is a broader label such as `Net Loss - ad hoc` can still satisfy DFM/Dataset loads by their visible instance name. Manual `source_kind: "input"` caches are never cleared or regenerated by ArcRhoTri execution; the runtime uses the exact cache when present, can derive coarser period requests from finer cumulative caches (for example quarterly to annual), and returns an explicit local-cache error when only a coarser fixed-size cache exists or no input sidecar is found. `arcrho_api.triangle_rollup` owns that roll-up arithmetic for the app server and the Engine bundle alike, and every roll-up is valued on the project's Development End Date: `dataset_service.valuation_months` counts the months from the Origin Start Date through that date, from the same General Settings read that shapes a new dataset, and the runtime's derived view, the in-memory roll-up recipe, and `precedent_cache_service.rollup_rows` all pass it. Development periods are counted back from the valuation date, not forward from the origin, so the newest cell of every row lands on the Development End Date and the first development period is the short one: a triangle stored at 12/1 in a project valued at August reads its 8th, 20th, 32nd, ... stored columns as a 12/12 view (8m, 20m, 32m, ... as ResQ labels it) and its 2nd, 8th, 14th, ... as a 12/6 view, and the view has exactly the rows and columns a dataset created at the requested shape would have — an origin block the stored rows only partly fill is still a row, and the development period the valuation date falls in is still a column. A development-aligned cache is aggregated along its calendar diagonals, because a column of such a triangle holds one valuation date per origin row: every finer row of a block contributes the cell it holds at the coarse cell's valuation date, and a coarse cell whose parts are not all present stays blank instead of reporting a partial sum. A calendar-aligned cache is aggregated by block, since its columns already share a valuation date, and there a missing finer cell counts as nothing contributed and the last period is the short one. A roll-up is refused when the requested periods are not whole multiples of the cached ones, and — for a development-aligned cache whose origins are being coarsened — when the cached origin period is not a whole number of its own development periods, because the rows of a block would then share no valuation date. DFM/local-only cache checks also inspect generated local triangle sidecars, and generated input triangles may fall through to ArcRhoTri generation for a missing requested shape as long as the base sidecar exists. Runtime engine cache creation writes the base sidecar when it is missing; when a generated cache is refreshed, the existing base sidecar updates `csv_file`, current request metadata, and modification/audit metadata so method-backed dependents can be marked for review.
- Persists Notes only in the owning dataset sidecar at `projects/<project>/data/<ReservingClassFolder>/sidecars/<DatasetName>.json`. DSV and every method page read and write that same `notes` field; no standalone notes JSON is created or indexed. A required index rebuild migrates a legacy standalone notes file into an existing sidecar that has no `notes` field, then deletes the legacy file; valid current indexes remain scan-free.
- Cached dataset lookup returns a valid current `index.json` directly without scanning its detail folders. When a rebuild is required, the builder scans the selected reserving-class folder's `datasets/`, `methods/`, and `sidecars/` children, matching CSV caches plus `DFM@...`, `RS@...`, `BF@...`, `BSSR@...`, and `BSCRA@...` method JSON back to logical instance-name candidates after applying the same server-side folder/file sanitizers used by runtime cache writes. Filename-derived names and metadata payload names are decoded from the reversible `_%XX_` form before the logical rows are persisted, so encoded sidecar/method payloads and decoded file-derived names collapse to one Project Instance row; when both metadata and filename names are present, the metadata `dataset_name` becomes the row `name` and the filename name is only an alias. The rebuilt payload keeps a short `sha256:` `folder_signature` derived from physical file names, sizes, modification times, and folder existence for stale-content detection, while the saved `files` list remains a compact logical instance list for Project Instance. Each cached instance row stores `name` as the user-visible instance Name, `dataset_type` as the Dataset Type used to open/decorate that instance, and `dataset_category` as the category used by Project Instance and Result Selection filters.
- Review status is attached only to datasets owned by a method. Plain input datasets and app-calculated datasets, including formula vectors between method outputs, remain Current even when their values refresh. Dependency propagation still traverses those plain datasets so any later method-backed descendants become Review Needed. Status records human acknowledgement, while refresh, propagation, and index outcomes are reported separately.
