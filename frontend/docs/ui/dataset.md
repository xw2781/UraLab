# Frontend: Dataset

## Purpose
<!-- MANUAL:BEGIN -->
Dataset editing and analysis page used inside shell tabs.
It owns the Dataset workflow across Details, Data, Chart, Notes, Links, and Audit Log views, with `Data` as the default tab and Links immediately after Notes.
The page validates Project Name, Reserving Class, and Dataset Type before running ArcRhoTri, renders/caches the resulting triangle data, and publishes status/history updates back to the shell.
Dataset Notes uses the shared notes editor, including rendered file-path links and its file actions.
Dataset Links uses the shared external-links table to inventory and refresh Excel sources used by editable Data cells, and to break sources into the current hard-coded values.
Implementation details should stay in the generated entrypoint/key-file sections or the focused behavior sections below, not in this overview.
<!-- MANUAL:END -->

## External Interfaces
<!-- MANUAL:BEGIN -->
- Calls app-server dataset/arcrho endpoints plus valid-value list endpoints (`/dataset_types`, `/reserving_class_*`, `/arcrho/projects`).
- Uses `/project-user-preferences` to persist and restore the shared project-specific last Reserving Class path plus the Dataset Viewer Dataset Name in `projects/<project>/users/<windows-login>/preferences.json`.
- Sends status/hotkey/close signals to parent shell, and consumes `arcrho:dataset-save` from shell or Project Instance hosts to run the same save flow as the Dataset Save button.
- Publishes dataset input updates and browsing-history updates to shell via `arcrho:dataset-settings-changed` and `arcrho:browsing-history-updated`.
- Publishes `arcrho:calculated-datasets-updated` after a save/run recalculates dependent datasets, and consumes the same shell-broadcast report from Dataset or DFM saves; open Dataset tabs/windows auto-reload when their current project, reserving class, and dataset name match an updated calculated output. Tabs with unsaved grid/settings/Notes edits show a status warning instead of reloading.
- Publishes `arcrho:dataset-dirty` while saved sidecar settings or Notes have unsaved changes, then uses `arcrho:dataset-close-confirmed` after the user confirms discard in the shared page-local close dialog.
- Dataset uses `ui/shared/tabbed_page/` for reusable tab chrome and the matching `ui/shared/tabs/data/`, `ui/shared/tabs/details/`, `ui/shared/tabs/notes/`, `ui/shared/tabs/links/`, and `ui/shared/tabs/audit_log/` modules for shared tab presentation/runtime. Dataset Viewer modules still own sidecar persistence, dirty state, save/close coordination, Chart behavior, and Dataset Viewer-specific page composition; the established Dataset tab IDs and `arcrho:*` contracts remain unchanged.
- `Ctrl+PageUp` and `Ctrl+PageDown` cycle backward and forward through Dataset Viewer tabs with wraparound. The shared tab runtime handles the keys inside the page, while shell and Project Instance hosts forward the same command when focus has not yet entered the Dataset iframe.
- Dataset loads feature-neutral page/control primitives from `ui/shared/components/`, the app-wide scrollbar treatment from `ui/shared/styles/scrollbars.css`, and spreadsheet primitives from `ui/shared/components/spreadsheet/`. Dataset Viewer-only chart, formula/relationship, save/recalculate, and page-layout styling remains in `ui/dataset_viewer/dataset_viewer.css`; method pages do not import that Dataset Viewer-local stylesheet.
- The host-neutral Data-tab runtime lives under `ui/shared/tabs/data/`: `data_tab_controller.js` remains the stable public facade while focused sibling modules own dependency bridging, Details, inputs, requests, persistence, and the active dataset session. Dataset API/config/state, header, dependency, formatting, and run services live under `ui/shared/dataset/`; the dataset-name picker lives under `ui/shared/components/pickers/`. Dataset Viewer supplies its page, Chart, Notes, and host adapters from `ui/dataset_viewer/`, while DFM supplies its own adapter from `ui/method_pages/dfm/`.
- Inactive Dataset tabs use the same pale hover fill as Bornhuetter Ferguson tabs, while active-tab fill and weight remain unchanged.
- The Data grid's right-click menu contains a standard `Show/Hide subtotal` command that toggles whether the derived footer `Total` row is visible. In Transposed mode it controls the equivalent right-side `Total` column. The setting defaults on for existing sidecars that predate the field and is saved per dataset instance as sidecar `show_subtotal`; formula text no longer overrides the user's Dataset Viewer choice. DFM keeps its separate formula-based total policy because it does not expose this Dataset Viewer control. The same menu carries `Clear data`, shown beside `Paste` only while the grid is editable: it sets every cell the grid shows to `0` through the same fill the Delete key applies to a selection, which is the state that lets the length and `Stored at` controls open up again on a hand-entered dataset.
- In the Data tab, transposed datasets show totals as a single right-side `Total` column instead of repeating totals across a footer row under each origin column.
- Open-window change alert: durable (non-temporary, non-draft) Dataset Viewer windows poll `/object_change/fingerprint` for their sidecar through `ui/shared/services/object_change_watch.js` and show a one-time "close and reopen" message box when another user or the Engine dependent-propagation job rewrites the dataset. The shared Data tab reports save/run boundaries and durable load completions through `ui/shared/tabs/data/data_tab_change_watch_port.js`, so the page pauses and rebases the watch around its own saves and never alerts on them; hosts that leave the port unconfigured (DFM's embedded Data tab) are unaffected. The alert offers a Refresh Now action that reloads the window in place when it has no unsaved changes. The alert names the writer: the window reads the object's recorded attribution once after the fingerprint moved and says who saved it, or which automation task rewrote it and the account it ran as. A stale mapped-drive read of the window's own save never raises it: a change is only reported when the object's recorded write is newer than what this window already has. Dependent-propagation jobs started by this app instance never raise the alert: Project Instance broadcasts `arcrho:dependent-propagation-started`/`-finished` scope messages that pause the watch for the job's project and reserving class and rebase it at the terminal status.

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Uses in-page mutable state for active dataset and selection.
- Reads and caches valid value lists via `ui/shared/services/valid_value_lists.js` for:
  - project names from the project index
  - dataset names by project
  - reserving class paths by project
- Reserving-class path normalization preserves literal `/` characters inside a class name; only `\` is treated as the segment delimiter for validation/history keys.
- Dataset-side reserving path list loading does not auto-crawl `/reserving_class_path_tree/children`; child-path hydration is opt-in to avoid background request storms.
- Caches reserving-class type names from `/reserving_class_types` and validates input paths by segment membership in the Name column.
- Reserving-class tree view toggle preferences (auto-expand/auto-close), picker window sizing/favorite paths, favorite nicknames, favorite folders, and hidden path list are stored per project/user in `projects/<project>/users/<windows-login>/preferences.json`. Final reserving-class paths are always selected with a single click. The favorite path context menu can rename a favorite or revert a custom nickname back to the original raw path label.
- Reserving-class tree favorites appear in a collapsible `Favorite` section above the collapsible `All Paths` tree. New favorite rows display the full raw path until renamed; after rename, only the custom favorite name is shown. Favorite rows include the same value-type icon and level label treatment as source rows plus a slashed-star remove button. When no favorites exist, the empty state instructs users to click the star beside an All Paths entry. Selecting a favorite applies its raw path to the Reserving Class input with the same single-click behavior as source tree paths. Right-click actions can copy the raw path, rename inline, remove from Favorite, or reveal the favorite in the source tree. The Favorite section supports custom folders: users can add folders from the section header, delete or rename folders inline from the folder context menu, and drag favorite rows into a folder or back to the root Favorite list.
- Reserving-class tree hide removes the hidden node in place with a short collapse animation instead of rebuilding the full tree. The tree toolbar includes an eye button next to the filter button, and the tree node right-click menu also includes `Hidden Paths...`; both open a small live-updating window listing hidden paths with multi-select `Unhide Selected` and `Unhide All` actions. Full tree refreshes, such as unhide actions, preserve the current tree scroll offset and expanded paths, then swap in the refreshed tree after it is laid out so the visible area remains stable instead of jumping back to the top or visibly flickering.
- Dataset Type picker preferences (`Double Click to Select`, `Close Window after Selection`) are also stored per project/user so they copy with project duplication.
- On project switch, current Reserving Class input is revalidated against the new project's reserving-class type names; valid paths are retained and invalid paths are cleared.
- Origin Length and Development Length are independent controls. When either length changes, the other length is adjusted only if the current pair breaks the required relationship (`Origin Length >= Development Length` and `Origin Length = Development Length * integer`).
- A Vector dataset has no development dimension, so the Data tab locks its Development Length control: it displays `0`, is dimmed with no caret, drops out of the tab order, and cannot be opened by click, keyboard, or wheel, with a tooltip giving the reason. The lock is display-only - the value stored in the sidecar is untouched, because the ArcRhoVec request sends only `PeriodLength` and rewriting the stored length would mark an unedited dataset dirty. Locking is generic to the top-bar length controls (`setLenSelectLock` marks the wrap with `data-locked-value`, which every label repaint honours), and the Data tab reapplies it whenever the save UI refreshes or saved settings are applied to the controls, so it follows a switch between a Triangle and a Vector Dataset Type.
- Origin Length and Development Length are the shape the dataset is *displayed* at, and the sidecar's stored pair is the shape its own CSV is really held at. A `Stored at` control sits beside each length, as it does in ResQ's Edit Triangle dialog, and reads the period taken from the sidecar load and refreshed by the sidecar save. The origin one is never editable: as in ResQ, the Origin Length control fixes the origin store while the dataset is empty, so the readout is dimmed with the reason on hover. The development one is a live control only while a manual input dataset's own file still holds nothing but blanks and zeros, which is the one time the store can move; it offers the periods that divide the displayed Development Length, out of the same `LEN_CHOICES` ladder, and lowering it leaves the display alone so the grid keeps the shape on screen while the next save writes the finer file. The question is asked of the file, not of the grid on screen: as in ResQ, the store is fixed by the first value a dataset is *saved* with, so a block pasted at the coarser display and not yet saved leaves the control live and travels to the server together with the period the user chose. An edit writes straight into the grid model and the cell's old value is gone with it, so `savedDatasetHoldsNoValue` reads the grid only while nothing is marked as an edit and keeps that answer until the next load or save replaces it. The length ladder follows the same reading through `manualDatasetLadderFloor`, which drops back to the shape unsaved values were entered at so the list never offers a length `validateManualDatasetLengthChange` would snap straight back. Otherwise it is dimmed and says `Stored at can be changed only while the dataset is empty.`. The DFM Details tab shows no `Stored at` control at all, since it does not save the dataset sidecar; `updateStoredLengthControls` returns at once on that host. A display-length change on a still-empty dataset resets both `Stored at` values to the display, as ResQ does. A Vector shows `0` on both its Development Length and its development `Stored at`. Each length control offers only whole multiples of its own stored length, origin and development independently and for every source kind, filtered out of that same ladder rather than a second list; a display length the narrowed list no longer carries falls back to the stored length itself. A length control carries no hover hint of its own: the `Stored at` value beside it is the answer, and the only tooltip left on the control is the reason it is locked. The window opens at the display shape the sidecar saved: the launch query's lengths are applied first and the sidecar's own display pair replaces them once it loads, and the narrowing runs before that value is written so a saved shape is never dropped for want of an option.
- The two axes part company on a display coarser than the stored shape, as they do in ResQ. A coarser **origin** display is a calendar diagonal of several stored rows with no single cell behind it, so the grid, the Links tab, and paste are read-only there and a refused edit says why inside the window: a `Read-only view` message box reading `Values can be entered only at the stored origin period (Origin 1). Set the origin length back to edit.` (a Vector names one `Period` and keeps its own wording). Every refusal the grid reports — a generated dataset's as well — opens that box rather than writing to the shell's status line, which sits below every page and is easily missed; one box stands at a time, so a number typed at a locked grid explains itself once instead of once per keystroke. A coarser **development** display does have one cell behind each column -- the stored cell at that column's own age -- so typing, paste, and links stay live: the grid is sent at the display shape and the save scatters it into the store, which is why the status line carries `Saving here writes each value into the stored period (Development 1) at its own column age and clears the stored periods between.` for as long as that view is on screen. That sentence reads the period the *next save* will write at (`getStoredLengthControlPair`), not the one the sidecar already records, so an empty dataset whose `Stored at` has just been lowered says what a save will do before it has been saved once. `datasetOriginDisplayIsCoarserThanStored` is the only one of the two that `isDatasetReadOnly` reads, alongside the read-only source kinds, and one `getDatasetReadOnlyMessage` owns the wording every refusal reports, so a coarser view is never explained as a generated dataset. A length change is still a dirty display setting: Save stays available and persists the new display shape. Links follow the display, not the store. A saved link names a cell of the grid its dataset was shown at when the sidecar was written, so a triangle held monthly under a yearly display carries yearly links and they stay live at that display: a value can be typed and an Excel range pasted at Origin 12 / Development 12 over a file stored at Development 1, exactly as in ResQ. What holds them still is the display moving off the lengths they were written at — `datasetDisplayIsAtLinkedShape` is false, comparing the length controls with the sidecar's linked pair (`linked_origin_length` / `linked_development_length`, `linked_period_length` on a vector, read by `datasetLinkedDisplayLengths`; links entered and not yet saved belong to the display the sidecar was last loaded or saved with), never with the stored pair or the display pair — because every cell of any other view stands for other cells entirely. There the whole link inventory stands still: no cell is painted with a link contour, no cell answers what it is linked to, a cell edit releases nothing, a link cannot be entered or broken (`linksControllerIsReadOnly` reads the same test), the opening link check does not run, neither does a refresh from the Links tab. The save itself goes through: the new display lengths are recorded while the server keeps the linked pair as it was, because the links it received are the ones it already holds, so a monthly dataset linked to an Excel range can be shown and saved yearly and its links wait at the monthly view. The linked pair moves only with a save whose links differ from the sidecar's, and it goes when the last link does. A dataset that still holds nothing, or holds no link, is never held still. The links themselves are untouched in the sidecar and come back the moment the lengths do; the Links tab still lists them, with the Value and Destination columns — which are read off the grid on screen — left blank rather than quoting a cell the link never named. In place of a formula, every cell of a linked dataset opens the floating formula bar carrying one sentence instead: `This dataset's cells are linked. Set Origin Length to 12 and Development Length to 12 to view or edit the formula.`, naming only the lengths that actually moved and using a Vector's own `Set the length to 12` wording. `datasetOffLinkedShapeLinkHint` owns that sentence. The bar wears its `isNote` state for it — muted, in the interface font rather than the formula's monospace, and never typed into, whatever the caller asks for — so a notice can never be mistaken for a formula waiting to be edited.
- New standalone Dataset tabs read the last selected Project Name from `%APPDATA%\ArcRho\local_project_prefs.json` first, then load that project's `lastReservingClassPath` and `datasetViewer.datasetName` from `projects/<project>/users/<windows-login>/preferences.json` to restore the last Reserving Class and Dataset Name for that project. The project tree picker also reads the same local preference file and shows a blue virtual `Recent Projects` folder above the real project folders with the last three picker-selected project names.
- Stores the project-specific last Reserving Class under shared `lastReservingClassPath` and Dataset Name under `datasetViewer.datasetName`, then reuses them after a project is selected when no query/workflow values override the inputs.
- Workflow-embedded Dataset pages can bind Project and Reserving Class inputs to Global Control defaults, displaying `Default Project (<project>)` and `Default Path (<path>)` while resolving backend requests to the current default values.
- Persists last-viewed dataset inputs globally, including Cumulative, Transposed, and Development/Calendar mode, and restores them when opening a new Dataset tab.
- Dataset loading has no built-in sample dataset ID. If neither the page URL nor saved selections provide a dataset ID, the page shows a neutral no-selection state and waits for valid Project, Reserving Class, and Dataset inputs instead of issuing a dataset request.
- A Dataset Viewer opened for an existing dataset from Project Instance uses one `/dataset/cache/load` request that reads the exact `<DatasetName>.json` sidecar and its named CSV cache. It applies lengths, formatting, notes, graph/audit data, origin labels, and grid values from that response without loading project, reserving-class, or Dataset Type validation lists and without rereading `index.json`. When an older sidecar has no valid origin labels, the same aggregate request resolves authoritative project headers before returning so CSV rows are not hidden; sidecars with complete labels retain the two-file fast path, and the origin-header, development-header, and Dataset Type hydration reads run concurrently server-side so a mapped-drive open pays one hydration chain of latency. A triangle's column ages are never taken from the sidecar: Project Settings own the development axis as they own the origin one, so `_resolve_development_labels` asks the project for the ages of the view being loaded and cuts them to the columns the dataset has. A project valued in August reads 8m, 20m, 32m at a yearly view and 1m, 2m, 3m at a monthly file, whatever list the sidecar still carries from the importer or creator that wrote it; that list answers only when the project headers cannot be read at all, and only when it has one label per column. The request carries `at_display_shape`, so a hand-entered dataset whose sidecar shows it coarser than its file is held at arrives already rolled up to that display shape, with `origin_length`/`development_length` naming the view and the `stored_*` pair naming the file, and the window opens at the shape the sidecar saved rather than the file's own; the roll-up is the same in-memory view a run builds and is never written beside the file. Standalone, draft, refresh, and generated-cache workflows keep their full validation/materialization paths. A hand-entered Triangle's load carries the same calendar diagonal as a new grid: the mask the response returns is the file's own blanks narrowed to the cells `triangle_grid_shape` gives that display shape, so a figure an older file holds past the diagonal is neither shown nor editable and the next save writes that cell blank. Only `source_kind: "input"` triangles are narrowed; a generated or calculated dataset keeps the mask its file gives it.
- Other Dataset page opens load the base generated dataset sidecar `<DatasetName>.json` for the selected project/reserving-class/dataset and apply its saved `origin_length`, `development_length`, cumulative, transposed, calendar, `show_subtotal`, `decimal_places`, and `number_format` Data-tab settings before loading the triangle.
- The Details tab is two sections in the shared order: identity - Name, Dataset Type, Project Name, Segment - then what the dataset is computed from and what consumes it - Formula, Precedents, Dependents - separated by one light rule. There is no shape-and-precision section here: Origin Length, Development Length, Number Format, and Decimal Places stay in the Data tab's top bar, beside the triangle they reformat. `Segment` is this page's label for the reserving-class path; it is read-only and has no browse button, because every host fixes it. `Dataset Type` and `Project Name` open their lists from their own browse button only - clicking into the text box places a caret, while typing filters and `ArrowDown` opens the list. The Project row is the host-fixed row described in the Frontend Behavior Contract: it is hidden except in a Workflow step, so a Project Instance window opens on Name while `#projectSelect` keeps holding the project the Data-tab runtime reads. Its contents take their label and field look from the shared Details primitive `details_form_layout.css`, which the page stylesheet must not restate; see the Frontend Behavior Contract. The generic `.small` utility in particular must stay off Details labels: it loads after the shared sheet and silently overrode the shared label size and colour on this page alone. Details inputs and graph boxes fill the available panel width and resize with the window. The Formula field renders the expression as text on a field the same height as every other Details row, carrying the read-only fill: the formula belongs to the dataset's Dataset Type in Project Settings and cannot be edited from here. Operators are the characters the user typed, and a recognized source is its name in double quotes. The quotes are drawn whether or not the stored formula carried them, because a dataset name contains spaces and would otherwise read as several operands. The text comes from the shared `formatDetailsFormulaText`, which the Project Settings Dataset Types table and the Project Instance dataset table also use, so the same formula reads identically in all three places. The formula is deliberately not a set of links - the Precedents row directly below lists the same sources as chips and owns opening them, so a second, differently-shaped way in would only make the expression harder to read. A Precedents or Dependents chip asks the Project Instance host to open the related dataset or, when it is backed by a DFM, Result Selection, Bornhuetter Ferguson, Cape Cod, or Berquist Sherman method, the related method window for the same reserving-class path. Whether a source is itself calculated is marked once, on its Precedents chip. Empty Formula, Precedents, and Dependents boxes stay blank, with empty Formula shown as a compact grey one-line box. The Precedents field is populated directly from the sidecar `Precedents` graph so it can show sources not present in the formula text. The Dependents field is populated from the sidecar graph with matching dataset chips; hovering a precedent or dependent shows its formula in an app-styled tooltip through the same plain-text renderer, prefixed by an `=`, so one formula never reads two ways in one tab; and formula tooltips shrink to the widest wrapped row when the content hits the maximum width. Clicking either a precedent or dependent opens its method window when the related dataset is method-backed and otherwise opens Dataset Viewer.
- Stores latest browsing history entries via `browsing_history.js` (project + reserving class + dataset).
- Rejects invalid typed values on change/Enter and blocks ArcRhoTri requests until all 3 inputs are valid.
- The Loading Dataset popup itself is one instance of the shared progress popup (`ui/shared/components/progress_popup/`), which owns the overlay markup, the sweep spinner, and the elapsed counter; the run controller only decides when to raise and hide it, and pages that suppress the popup never build one. `createArcRhoBusyOverlay` wraps one popup instance in a scope counter so overlapping work keeps a single popup up until the last scope ends.
- The saving animation is the same popup driven by the shared save-progress framework (`ui/shared/components/progress_popup/save_progress.js`), and every window that saves an ArcRho object uses it: Dataset, DFM, Result Selection, Bornhuetter Ferguson, Cape Cod, and Berquist Sherman. A page creates one `createArcRhoSaveProgress({ subject })` instance and wraps its save entry point in `run`, so the save is blocked behind a card titled `Saving <subject>` for the whole round trip and every entry point into that save - save bar, keyboard save, shell save message, and bridge-dialog save - is covered by construction. The framework owns the wording: the card opens on `Preparing the <noun> before saving.`, `progress.writing()` switches it to `Saving the <noun> and updating dependent objects.`, and the noun is `method` everywhere except the Dataset window, which passes `dataset`. `progress.finish()` drops the spinner before any dialog the save opens - the post-save review warning, the Engine-unavailable message box, the dataset recalculation dialog - so no dialog opens behind it, and `run` always dismisses on the way out, including when the save throws. Overlapping saves share one popup through the same scope counter, and the elapsed counter matches the Loading Dataset popup.

- A linked Dataset cell whose Excel reference failed validation keeps its saved value and renders in red (`--ar-spreadsheet-link-error-text`, with a Dark deviation in `themes/dark.css`) until the reference is fixed, so the broken cells stay identifiable after the message box is dismissed. A refresh applies each link whole or not at all, so a link with one broken source cell leaves every one of its destinations on the saved values; only the source cells that actually failed are marked red and named. The marking clears when that link next refreshes successfully, or when the link is broken or hard-coded. A refresh is an action the user asked for, so one that does not do what was asked always reports in the window rather than only in the status bar: failures that carry a named reference are listed in the same **Excel Link Reference Error** box, and a failure with no reference to name — the batch request itself did not come back — opens an **Excel Refresh Failed** box giving the cell count, the fact that the saved values are kept, and whatever reason the request returned. The status bar is left for a refresh that succeeded. The automatic open-time check is not user-initiated, so a check that cannot run still reports quietly there.
- The Dataset page Save/Cancel row uses a reserved bottom frame across all Dataset tabs, matching the DFM page pattern so large Data tables scroll above the buttons instead of underneath them. Save writes the Details `Name` as the instance name, the selected Dataset Type, current Origin Length, Development Length, Cumulative, Transposed, Calendar, Show subtotal, Decimal Places, and Number Format values, and dirty Notes; for Project Instance non-generated drafts and existing manual input datasets, Save also writes the current Data grid values to the backing CSV and stores that file name in the sidecar. Background Data-tab runs may create or reuse a length-scoped CSV cache for preview, but do not update the user-editable source sidecar or clear the unsaved settings state. When a background run generates or derives a cache, it writes only a technical record containing per-CSV processing provenance plus a size, modification-time, and SHA-256 content fingerprint, so a later run can safely reuse that exact file; it does not save Data-tab settings or audit history. Only Save commits those settings. Cancel closes the Dataset window; when dirty, it opens the shared page-local close confirmation where the default Yes action discards unsaved changes, while No, Escape, clicking the backdrop, or closing the box returns to the unsaved page. The dialog states, "Unsaved changes will be discarded and the window will close." The modal stays inside the Dataset page and makes the rest of that page inert while it is open. CSV filenames still distinguish cumulative, incremental, development-view, and calendar-view variants.
- While hosted in Project Instance, dirty manual Dataset grid values publish `arcrho:dependency-source-preview` messages with both latest-diagonal/vector values and full matrix values. Dirty DFM output vectors publish the same preview contract. Open dependent Result Selection windows use the vector values, while DFM input-triangle windows and matching Dataset Viewer windows can render the temporary in-memory table without marking themselves dirty. A Dataset Viewer applies a preview only when the message or its current loaded model provides valid consecutive origin labels matching the selected period type and preview row count; otherwise it leaves the current grid unchanged and reports the Origin Start Date correction instead of creating numeric row labels. Project Instance also requests in-memory app-calculated previews for downstream calculated Dataset Types and publishes target-specific preview messages so open calculated Dataset windows, and Result Selection method sources that reference them, can update before the upstream source is saved. Typing or pasting unsaved Dataset values or Excel references updates only this in-memory dirty/preview flow and does not request a Project Instance disk-backed dataset inventory refresh; the persisted inventory refresh remains tied to Save or an explicit Project Instance refresh. Save, Cancel, or close-without-save publishes `arcrho:dependency-source-cleared`, so dependents reload the source from persisted disk data.
- The Data tab Number Format field is the shared `arNumberFormat*` control in `ui/shared/components/pickers/number_format_field.{js,css}`, which Berquist Sherman Details also uses: an editable pattern input with an in-field caret that lists the canonical presets under it. The component owns opening, rendering, dismissal, and ARIA state; the page owns what a chosen preset means, because the Dataset Viewer re-derives Decimal Places and repaints its grid while a method page records the pair and marks itself dirty. Only the top-bar footprint stays in `dataset_viewer.css`. It offers preset suggestions for `0,000`, `0.0%`, `0,000.00`, and `0`; changing it marks dataset settings dirty, immediately refreshes the grid/chart display, and persists as sidecar `number_format` on Save. Number Format and Decimal Places use the shared filled-caret dropdown/stepper arrow style, with muted arrows at rest and stronger arrows on hover, focus, or open. Decimal Places remains the source of truth for fractional digits, so changing Decimal Places rewrites the visible format pattern (for example, `0,000.00` becomes `0,000.0` when Decimal Places changes to `1`) and persists as sidecar `decimal_places`.
- The Chart tab uses the same shared right-side legend panel as Result Selection: it shows the visible-series count, full-row visibility checkboxes, and line-and-marker swatches. One series always remains visible; right-clicking a legend item isolates that series, and right-clicking the sole visible item restores all series. In narrow windows the legend moves below the chart.
- The Audit Log tab renders the dataset sidecar `audit_log` entries newest first, with Event Date displayed as `M/D/YYYY h:mm:ss AM`. It uses the shared `ui/shared/tabs/audit_log/` presentation also consumed by method pages, so the compact bounded table, sticky header, plain-text Action values, row hover feedback, loading/error/empty states, continuous square frame, and quiet scrollbar behavior remain consistent. The scrollbar tray consumes space only while overflow requires a scrollbar. Dataset sidecar inserts, metadata saves, grid value patch saves, ArcRhoTri sidecar creation, and calculated dataset recalculation append records capped at 50 entries with `event_date`, `action`, `change_info`, and `user`; `change_info` is blank for `Insert` and `Values` for `Update`.
- When Dataset saves, grid patch saves, or ArcRhoTri refreshes trigger calculated-dataset or method updates, the Dataset page shows a compact modal report with the ordered recalculation chain, decoded reserving-class paths, and skipped/error details. The source Dataset remains saved if a downstream DFM, Result Selection, or BF refresh fails, but the page reports that partial result as a warning with the downstream error instead of showing an unqualified save success.
- Dataset Viewer query parameters accept explicit origin/development lengths, an initial tab, a Project Instance draft mode, an optional `data_format`, an explicit `ds` cache id, and a read-only flag. Draft launches from Project Instance open on Details, honor the provided project, reserving-class path, dataset type, data format, and lengths, but skip the initial auto-run and build an editable zero-filled Data-tab placeholder from validated current-project origin labels and current development labels. A missing/invalid origin-header response leaves the draft grid unloaded, reports the Project Settings error, and blocks Save; drafts never substitute numeric origin rows. A Triangle draft takes its cells from the project rather than from a rule of the window's own: `GET /datasets/triangle-shape` answers with the rows, columns, and cell mask a dataset created at those two lengths would be written with, and the grid stops where that mask stops -- the project's calendar diagonal, as the Origin Start Date, Origin End Date, and Development End Date fix it. It matters whenever the two period lengths differ: a quarterly development of annual origins drops four columns a row and not one, and the project's development headers can run past the valuation date, so the columns are the shape's rather than the headers'. A cell outside the mask is blank, cannot be typed into or pasted over, and is written blank when the draft is saved. A Vector has no diagonal and keeps every cell of its one column, so it asks for no shape. A draft that has not been persisted yet is always save-eligible: it opens fully prefilled from the picked Dataset Type, so Save and `Ctrl`+`S` stay enabled with no control or grid edit, and the first save writes the placeholder grid even when the user typed no values. Save returns to disabled once the draft is saved, and renaming an already saved draft makes it save-eligible again. That pending-save state is deliberately not the tab dirty state: an untouched draft still closes without a discard confirmation. Saving a draft persists the placeholder grid to the length/mode-scoped CSV, records the returned `ds_id`, and keeps later grid edits attached to that CSV-backed cache. Manual input Triangle/Vector datasets keep Cumulative and Development/Calendar mode locked; if any stored cell is non-zero, the Origin Length and Development Length controls cannot be lowered below the lengths the values are stored at until all cells are set to `0`. Once they are -- `Clear data` on the grid's right-click menu does it in one step -- a length change no longer reloads the dataset's file, which would put the old values back over the zeros: `refreshClearedDatasetModel` rebuilds the grid empty at the new lengths through the draft's own zero-filled model builder, marks every cell as an edit so the save carries the grid, and releases the stored period (`releaseStoredShape`), so `storedLengthIsPending` stays true after values are pasted or typed in and the ladder is not narrowed back to the file's period. While those values are unsaved the length controls are held at the shape they were entered at, with a status line saying to save or clear first, and the save carries `stored_values_cleared: true` so the server writes a new file at that shape and deletes the old one. A cancel or a fresh sidecar answer clears the release. The floor is the stored pair, not the last saved display shape, so a dataset viewed at a coarser length can always be brought back down to the shape its values live at and edited again. In draft mode, Details `Name` defaults to the selected Dataset Type but remains editable as an independent instance name. Draft Dataset `Name` values must be unique within the selected reserving-class path; when the name already exists, the Details tab shows a floating warning tooltip beside the Name field and blocks Save and generation until the name changes. Existing dataset launches do not show the draft duplicate-name warning for their own name. Read-only launches disable manual CSV patch saves and reject grid paste edits. Loaded sidecars are editable only when `source_kind: "input"`; other source kinds such as `engine`, `calculated`, `dfm`, `result_selection`, or `bornhuetter_ferguson` force the grid into read-only mode.
- Right-clicking a Dataset page tab temporarily moves that live tab page into a draggable, resizable floating window inside the Dataset page, using the same shared tab pop-out behavior as DFM. The floated tab keeps its original controls, event handlers, and data state because the actual tab DOM is moved rather than cloned. Pop-out and dock use short fade/scale transitions. Floating titlebars support double-click maximize/restore and drag-from-maximized restore to the previous window size. Closing the floating window, right-clicking its titlebar, or right-clicking the grey popped tab button docks the tab back into the normal tab area. The Chart tab redraws after pop-out, dock, focus, and resize so the canvas fits the floating window; in the normal docked tab, the chart panel also stretches with the tab area and redraws when that panel size changes.
